## Issue 1 — No restart button after match end

- **State:** Done (M-TIER1-UX subtask 1). Restart flow extended via
  Match Phase state machine (M-TIER2-PHASE, landed 2026-04-19) —
  Restart now walks through the real `finished → setup → running`
  transitions instead of a hidden `self.running = True` toggle.
- **Category:** Bug / UX
- **Owner:** Chen (`game-core/` + HUD)
- **Merges with:** `CHEN_BACKLOG.md` #2 Match Phase state (the `finished`
  phase should expose restart)
- **Tier:** 1

**What:** When Red or Blue wins, the end-of-match overlay has no restart
control. The operator has to reload the browser page to start a new match.

**Why it matters:** Basic demo UX. Judges cannot run a second match without a
page refresh.

**Design target:** The `finished` phase of the Match Phase state machine
exposes a Restart button in the HUD. Click → frontend sends a `reset`
command over WebSocket → backend rebuilds `build_default_scenario()` and
starts a fresh match, phase transitions back to `setup` (or directly to
`running` for Tier 1 before deployment UI is in).

**Touchpoints:** `frontend/js/hud.js`, `frontend/style.css`,
`backend/server.py` (reset handler), `backend/sim/scenarios.py`.

## Issue 2 — HGV airburst counted as a base hit

- **State:** Done (M-TIER1-UX subtask 3). HGV now physically reaches
  ground via Issue #10 glide-path dive subtask (M-TIER1.5). Broad
  flyover rule extended to ballistic/cruise/drone in W5 (M-TIER2.5) —
  every non-nuclear threat now sets `requires_ground_impact=True`.
- **Category:** Bug / Rule fix
- **Owner:** Chen (`game-core/`)
- **Merges with:** N/A (future nuclear warhead will invert the new flag)
- **Tier:** 1

**What:** HGV currently triggers site damage even if it airbursts above the
site without reaching ground. The leak detector uses a 1500 m horizontal
disc with no ground-impact requirement for HGV.

**Why it matters:** Makes HGV effective kill probability higher than
intended.

**Design target:** Add a per-kind flag `requires_ground_impact: bool` to
`ThreatSpec`. For HGV, set it to `True`. The leak detector then requires
both the horizontal disc check **and** `z <= site_z + small_epsilon` before
deducting HP. Future nuclear warhead kind will keep the flag `False` to
preserve airburst semantics for that one kind.

**Touchpoints:** `backend/sim/world.py` (leak detection),
`backend/sim/types.py` (spec flag), `backend/sim/config.py` (per-kind
value).

**Related Tier 4 item:** Nuclear warhead kind uses
`requires_ground_impact=False`.

## Issue 4 — Raise speed slider cap to 20x

- **State:** Done (M-TIER1-SPEED)
- **Category:** UI contract gap
- **Owner:** Chen (`game-core/`)
- **Merges with:** `CHEN_BACKLOG.md` #1 "Align Speed Control With Runtime
  Capability"
- **Tier:** 1

**Key finding from 2026-04-19 audit:** The backend already implements the
correct "constant-dt, scale-step-count" shape. `dt` stays constant at
`config.DT = 0.05 s`, and `self.speed` scales the **step count per
wall-clock interval**, not `dt`. All reload / fuel / inter-shot CD timers
are stored as sim-time (comparisons against `world.t`, which advances by
constant `dt` per sim-tick), so they auto-scale with speed.

**Audit evidence:**
- `backend/server.py:43` — `dt = config.DT` (constant)
- `backend/server.py:54` — `n = max(1, int(sim_steps_per_stream *
  self.speed))` (scales step count)
- `backend/server.py:98–103` — handler validates speed in range 0.1–20.0
- `backend/sim/world.py:288` — `self.t += dt` (sim-time advance)
- `backend/sim/launcher.py:45–48, 53–54, 59, 63–65` — reload/CD use
  `t_now` comparisons
- `backend/sim/entities.py:552–553` — fuel uses `t_now` comparison

**Hard requirement satisfied:** A 1x run and a 20x run of the identical
scenario produce identical physics — same `dt`, same total sim steps for
equivalent sim-time, same integration precision. Intercept outcome is
independent of the speed multiplier.

**Design target:** Change the frontend slider range from `0.5x – 5.0x` to
`0.5x – 20.0x` (or `0.1x – 20.0x` for parity with the backend-validated
range). Displayed Mach / G / velocity numbers in the status panel are
unaffected — they show instantaneous physics state, not wall-clock rate.

**Touchpoints:** `frontend/index.html` (slider `min`/`max`/`step`),
`frontend/js/hud.js` (label rendering).

**Expected scope:** ~15 min.

## Issue 10 — HGV default behaviour: straight to pre-selected target + flyover fallback

- **State:** Partially done — HGV default glide-path dive landed
  (M-TIER1.5). Full unified contract (target_site_id field,
  maneuver_schedule, flyover fallback) remains Open, Tier 3.
- **Category:** Rule refinement + API contract clarification
- **Owner:** Chen (runtime) + Boyu (future real-time overrides)
- **Merges with:** Issues 11, 12 — combine into one unified threat-control
  contract
- **Tier:** 2 (runtime default + fallback) / 3 (contract publication to
  Boyu)

**What (observation):** Per Milestone I Task 3, HGV default is
"straight-line toward pre-selected target" with
`Threat.override_maneuver(turn_dir, g_load)` as the external control hook.
The operator reports HGV appearing to fly straight without a target —
runtime verification needed: does `red_ai._pick_target` actually produce
a `target_site_id` on HGV spawn, and does the entity's default steering
aim at that site?

**Design target (union of this and Issues 11, 12):**

Unified threat-control contract exposed on `Threat`:

- `target_site_id: int` — set at spawn, immutable. Default steering aims
  at this site's position. Applies to drone / cruise / ballistic / HGV.
- `maneuver_schedule: List[(time_offset_s, turn_dir, g_load, duration_s)]`
  — optional pre-set jink list. Each entry: at `time_offset_s` after
  spawn, apply `(turn_dir, g_load)` for `duration_s`, then return to
  default steering. Applies to drone, cruise, ballistic (Issues 11, 12).
- `override_maneuver(turn_dir, g_load)` — existing per-tick override.
  Used by HGV real-time control (Issue 10) and stealth-cruise terminal
  handover (Issue 12). Ignored on drone / cruise / ballistic.
- **Flyover fallback:** if the threat's ground-track has passed its
  `target_site_id` (e.g. dot product of velocity vs. vector-to-target
  becomes negative), auto-retarget to the nearest in-arena friendly site
  in front of the flight path.

**Touchpoints:** `backend/sim/types.py` (schedule + fallback fields on
`Threat`), `backend/sim/entities.py` (schedule consumer, flyover
detection, fallback), `backend/sim/red_ai.py` (spawn sets
`target_site_id` and optionally `maneuver_schedule`).

**Not doing now:** Boyu's policy layer that decides what schedule or
real-time override to emit. Chen produces the runtime hook + contract
doc; Boyu consumes it.

- **(b)** Exempt cruise from the ground-impact rule (flip
  `requires_ground_impact=False` on cruise_sub spec). Preserves
  the visible pop-up-then-strike narrative. Spec comment in
  `types.py:92` already leaves room for kinds to opt out for
  airburst-class threats.

**What:** Real-world cruise missiles use terrain contour matching to avoid flying into mountains. Currently the game has no elevation terrain — only 2D land/sea polygons — so cruise_sub flies at a fixed low altitude with no obstacle awareness. Once Sebastijan lands 3D terrain, cruise_sub needs obstacle-avoidance.

**Design target:**

1. `maps/` publishes `terrain.height_at(x, y) -> float` (elevation above sea level in metres) as a stable public API. Sebastijan owns the data + implementation. Out-of-bounds return value and unit convention (metres above sea level) agreed on Chen ↔ Sebastijan at publish time.
2. cruise_sub's update block in `entities.py` samples terrain height `N` metres ahead of the flight path each tick, compares against the cruise's current altitude + safety margin, and:
   - **Simple (Tier 3 target):** pitch up smoothly to clear the obstacle; resume sea-skimming after the obstacle passes.

3. Drone / ballistic / HGV are exempt — drone is intentionally "dumb / cheap / expendable"; ballistic arcs over terrain; HGV flies at 35 km cruise altitude so terrain is irrelevant.

**Touchpoints (future):** `backend/sim/terrain.py` (new `height_at` function), `backend/sim/entities.py` (cruise_sub update block adds terrain lookahead), `maps/` package data + `TERRAIN_PIPELINE.md` contract doc.

## Issue 19 — Blue AI pre-launch + loft guidance + data-link re-targeting (Oskar scope)

- **State:** Open (design spec captured 2026-04-20; implementation when Oskar owns `blue_ai.py`)
- **Category:** AI / contract design — consequence of the AWACS-data-link framing Chen committed to 2026-04-20
- **Owner:** Oskar (Blue AI) + Chen (any runtime hook Oskar needs)
- **Merges with:** Issue #15 (pac_3 htk default — balance drift explicitly promised to Oskar lead-prediction), Issue #14 (ballistic CEP vs leak disc — same class of problem), STATUS Known Limitation #3 (omniscient detection is already in place — no detection_range gate to remove), STATUS Known Limitation #4 (no real Red AI yet — this issue assumes Red AI side is symmetric on its own timeline)
- **Tier:** 3 (post Hack Day or in parallel with Oskar's track; not blocking the 2026-04-25 demo)

**What (empirical baseline from `backend/diag_hgv_blue.py`, 2026-04-20):** Single HGV aimed at east-side Firewatch Station (X=125.8 km) from Y=240 km far-north spawn, 3 trials varying the pac_2/pac_3 launcher Y position:

| Trial | pac_2 fire t / CPA | pac_3 fire t / CPA | HGV impact miss |
|---|---|---|---|
| Default layout | 32.9 s / 38.7 km | 36.0 s / 43.2 km | 137 m (hits target) |
| Launchers +30 km south | 27.2 s / 38.8 km | 30.2 s / 43.2 km | 137 m |
| Launchers −30 km north | 38.8 s / 53.0 km | 42.0 s / 55.1 km | 137 m |

Blue AI fires `pac_2`/`pac_3` at the instant each threat enters the static `max_range × LAUNCH_RANGE_MARGIN` gate — so this is **not** a gate-too-conservative bug and **not** a PN precision bug. By the time the gate triggers, HGV is ~10 s from ground impact; Mach-5 interceptor from ground zero cannot close on Mach-17 HGV in that window. Only one shot per launcher actually fires — reload cooldown exceeds the HGV's gate-traversal time so saturation (3-missile-per-threat) never engages. Launcher repositioning changes the fire-time but not the outcome — HGV miss distance against target is invariant at 137 m in all three east-side-target trials because no interceptor ever connects.

**Complementary baseline (`backend/diag_hgv_vs_blue.py`, 2026-04-20):** A second diagnostic sweeps four HGV-geometry × launcher-placement combinations against a dead-center target at PAC-3's own default position (75.3, 8.0)km. The critical finding is **Trial D**: with pac_3 forward-deployed to Y=40 km (roughly 30 km further north than default, well inside the threat envelope) and HGV aimed dead-centre at pac_3, pac_3 fires at t=24.5 s (vs t=36 s default — gate entered 11.5 s earlier) and **closes to CPA 164 m** (vs 43 km default — a 260× improvement). HGV dies mid-flight at 6.42 km altitude. This is ~100 m away from a direct kill (pac_3 `radius_direct` = 60 m). The implication for Oskar: pre-launch / lead-prediction is not the only handle — **forward deployment alone already closes most of the geometry gap under the current rule-based blue_ai**; pre-launch on top of a forward-placed pac_3 should consistently fall below the 60 m kill radius against dead-center threats. East-side threats (Firewatch target in the first diagnostic) remain out of reach without pre-launch because PAC-3's default X=75 km is 50 km off-axis from the target line.

**Why it matters:** HGVs are currently ~100% leak against geometry-distant targets (confirmed by STATUS Milestone I balance sweep: hgv 59-60 leaks across 3×20 matches ≈ 100% leak rate). Chen operator review 2026-04-20 confirmed this reproduces on the live browser demo after launcher drag-drop (M-TIER2-J Part 1). The gap is not a runtime bug — it is a direct consequence of how the rule-based blue_ai engagement ladder picks its firing window. Oskar's Blue AI track is where this gets fixed.

**Design target (three-part, all AI-layer work):**

1. **Pre-launch on predicted rendezvous point.** Blue AI fires `pac_3`/`pac_2` well before HGV / ballistic enters the static gate, using real-time threat position + velocity (omniscient detection is already in place — STATUS Known Limitation #3 is a feature under the AWACS framing, not a bug to fix) to compute a rendezvous point within interceptor fuel + range budget. Launch timing chosen so interceptor reaches the rendezvous point at the moment the threat arrives. Expected effect on the diag baseline: pac_3 CPA drops from ~43 km toward sub-100 m.

2. **Loft guidance (mid-course waypoint before terminal PN).** Pre-launched `pac_3`/`pac_2` follows a lofted trajectory — climbs to near-target altitude before switching to terminal PN — rather than the current "PN from launch" behaviour that wastes range on low-altitude pursuit. May require an interceptor guidance-mode addition in `backend/sim/entities.py` (mid-course waypoint then PN); if so Chen lands the runtime hook, Oskar plugs the decision into it.

3. **Data-link re-targeting.** An interceptor that misses its initial assigned target (or whose target dies from another shot / flyover / crash) re-acquires the highest-priority still-alive threat within its remaining fuel + range budget. Applies to every Blue kind EXCEPT `ciws` (which is a line-of-sight cannon, re-targeting semantically meaningless). "No missile wasted per engagement." Cleanly reuses the existing `blue_ai.assignments` map; new field on Interceptor tracks its currently assigned `target_id`, swappable mid-flight.

**Framing justification — Chen's AWACS assumption, 2026-04-20:** Both Red and Blue AI assume full real-time information from a background AWACS / data-link layer (already what the current omniscient `blue_ai` models). The pre-launch + re-target behaviours above are the natural consequence of that assumption and the Chen invariant "don't buff from thin air" — nothing is being invented; Blue is using information it already has. Keeps the arcade-game framing aligned with the Saab spec.

**Touchpoints (future Oskar + optional Chen runtime hooks):**
- `backend/sim/blue_ai.py` — new pre-launch decision path, lead-prediction math against `world.threats` state, re-target logic on interceptor miss
- `backend/sim/entities.py` — if loft guidance needs a new mode, Chen lands a mid-course-waypoint-then-PN option on `Interceptor`
- `backend/sim/types.py` — probable new `Interceptor.target_id` field (mutable, for re-target)
- `backend/sim/launcher.py` — nothing expected; launcher state stays the same
- Blue AI log lines describing `LEAD_PREDICT`, `LOFT`, `RETARGET` tags (demo legibility — keeps the right-panel log story-shaped)

**Verification harnesses:** Two deterministic single-HGV scripts landed 2026-04-20 alongside this issue, both self-contained and <15 s headless. Cheap to re-run as regression checks after Oskar's patches.

- `backend/diag_hgv_blue.py` — East-side-target sweep. HGV aimed at Firewatch Station (X=125.8 km), launcher Y offset ±30 km. Exposes the geometry-distant failure mode. Acceptance goal: pac_3 CPA drops from 43 km → sub-100 m in the default-layout trial.
- `backend/diag_hgv_vs_blue.py` — Dead-center + flanking sweep. 4 trials (default, flanking iris_t_slm, pac_3 rear Y=-15, pac_3 forward Y=40). Exposes how much of the gap is pure placement (Trial D: CPA 164 m with forward pac_3) vs fundamental pre-launch (east-side trials). Acceptance goal: every trial's best interceptor CPA falls below its `radius_direct`.
