## Issue 1 — No restart button after match end

- **State:** Done (M-TIER1-UX subtask 1)
- **Category:** Bug / UX
- **Owner:** Chen (`game-core/` + HUD)
- **Merges with:** `CHEN_BACKLOG.md` #2 Match Phase state (the `finished`
  phase should expose restart)
- **Tier:** 1

**What:** When Red or Blue wins, the end-of-match overlay has no restart
control. The operator has to reload the browser page to start a new match.

**Why it matters:** Basic demo UX. Judges cannot run a second match without a
page refresh.

**Design target:** The `finished` phase of the Match Phase state machine
exposes a Restart button in the HUD. Click → frontend sends a `reset`
command over WebSocket → backend rebuilds `build_default_scenario()` and
starts a fresh match, phase transitions back to `setup` (or directly to
`running` for Tier 1 before deployment UI is in).

**Touchpoints:** `frontend/js/hud.js`, `frontend/style.css`,
`backend/server.py` (reset handler), `backend/sim/scenarios.py`.

## Issue 2 — HGV airburst counted as a base hit

- **State:** Done (M-TIER1-UX subtask 3)
- **Category:** Bug / Rule fix
- **Owner:** Chen (`game-core/`)
- **Merges with:** N/A (future nuclear warhead will invert the new flag)
- **Tier:** 1

**What:** HGV currently triggers site damage even if it airbursts above the
site without reaching ground. The leak detector uses a 1500 m horizontal
disc with no ground-impact requirement for HGV.

**Why it matters:** Makes HGV effective kill probability higher than
intended.

**Design target:** Add a per-kind flag `requires_ground_impact: bool` to
`ThreatSpec`. For HGV, set it to `True`. The leak detector then requires
both the horizontal disc check **and** `z <= site_z + small_epsilon` before
deducting HP. Future nuclear warhead kind will keep the flag `False` to
preserve airburst semantics for that one kind.

**Touchpoints:** `backend/sim/world.py` (leak detection),
`backend/sim/types.py` (spec flag), `backend/sim/config.py` (per-kind
value).

**Related Tier 4 item:** Nuclear warhead kind uses
`requires_ground_impact=False`.

## Issue 4 — Raise speed slider cap to 20x

- **State:** Done (M-TIER1-SPEED)
- **Category:** UI contract gap
- **Owner:** Chen (`game-core/`)
- **Merges with:** `CHEN_BACKLOG.md` #1 "Align Speed Control With Runtime
  Capability"
- **Tier:** 1

**Key finding from 2026-04-19 audit:** The backend already implements the
correct "constant-dt, scale-step-count" shape. `dt` stays constant at
`config.DT = 0.05 s`, and `self.speed` scales the **step count per
wall-clock interval**, not `dt`. All reload / fuel / inter-shot CD timers
are stored as sim-time (comparisons against `world.t`, which advances by
constant `dt` per sim-tick), so they auto-scale with speed.

**Audit evidence:**
- `backend/server.py:43` — `dt = config.DT` (constant)
- `backend/server.py:54` — `n = max(1, int(sim_steps_per_stream *
  self.speed))` (scales step count)
- `backend/server.py:98–103` — handler validates speed in range 0.1–20.0
- `backend/sim/world.py:288` — `self.t += dt` (sim-time advance)
- `backend/sim/launcher.py:45–48, 53–54, 59, 63–65` — reload/CD use
  `t_now` comparisons
- `backend/sim/entities.py:552–553` — fuel uses `t_now` comparison

**Hard requirement satisfied:** A 1x run and a 20x run of the identical
scenario produce identical physics — same `dt`, same total sim steps for
equivalent sim-time, same integration precision. Intercept outcome is
independent of the speed multiplier.

**Design target:** Change the frontend slider range from `0.5x – 5.0x` to
`0.5x – 20.0x` (or `0.1x – 20.0x` for parity with the backend-validated
range). Displayed Mach / G / velocity numbers in the status panel are
unaffected — they show instantaneous physics state, not wall-clock rate.

**Touchpoints:** `frontend/index.html` (slider `min`/`max`/`step`),
`frontend/js/hud.js` (label rendering).

**Expected scope:** ~15 min.

## Issue 5 — Status-panel G-load always shows 0

- **State:** Done (M-TIER1-UX subtask 2)
- **Category:** Bug (rendering / data plumbing)
- **Owner:** Chen (`game-core/` + HUD)
- **Merges with:** N/A
- **Tier:** 1

**What:** The click-to-inspect status panel shows an instantaneous G-load
value that appears to always render as 0.

**Why it matters:** Visible artifact during a demo. Judges who click an
entity expect to see it manoeuvring.

**Related drift:** `KNOWN_DOC_RUNTIME_DRIFT.md` notes G-load is
"averaged over the snapshot tick, not instantaneous" — a known precision
issue, but the observed bug is stronger: it is always 0.

**Design target:** Diagnose whether (a) the backend is not populating
`entity.g_load` in the snapshot, (b) the frontend is reading the wrong
field, or (c) the averaging window makes G sample 0 for straight-flight
entities. Fix so a manoeuvring missile shows non-zero G in the panel
within 1 second of opening it.

**Touchpoints:** `backend/sim/entities.py` and wherever
`EntityState.to_dict()` is defined; `frontend/js/status_panel.js`.

## Issue 10 — HGV default behaviour: straight to pre-selected target + flyover fallback

- **State:** Default-straight is in (Milestone I Task 3); overflow fallback
  is missing; target-at-spawn needs runtime verification
- **Category:** Rule refinement + API contract clarification
- **Owner:** Chen (runtime) + Boyu (future real-time overrides)
- **Merges with:** Issues 11, 12 — combine into one unified threat-control
  contract
- **Tier:** 2 (runtime default + fallback) / 3 (contract publication to
  Boyu)

**What (observation):** Per Milestone I Task 3, HGV default is
"straight-line toward pre-selected target" with
`Threat.override_maneuver(turn_dir, g_load)` as the external control hook.
The operator reports HGV appearing to fly straight without a target —
runtime verification needed: does `red_ai._pick_target` actually produce
a `target_site_id` on HGV spawn, and does the entity's default steering
aim at that site?

**Design target (union of this and Issues 11, 12):**

Unified threat-control contract exposed on `Threat`:

- `target_site_id: int` — set at spawn, immutable. Default steering aims
  at this site's position. Applies to drone / cruise / ballistic / HGV.
- `maneuver_schedule: List[(time_offset_s, turn_dir, g_load, duration_s)]`
  — optional pre-set jink list. Each entry: at `time_offset_s` after
  spawn, apply `(turn_dir, g_load)` for `duration_s`, then return to
  default steering. Applies to drone, cruise, ballistic (Issues 11, 12).
- `override_maneuver(turn_dir, g_load)` — existing per-tick override.
  Used by HGV real-time control (Issue 10) and stealth-cruise terminal
  handover (Issue 12). Ignored on drone / cruise / ballistic.
- **Flyover fallback:** if the threat's ground-track has passed its
  `target_site_id` (e.g. dot product of velocity vs. vector-to-target
  becomes negative), auto-retarget to the nearest in-arena friendly site
  in front of the flight path.

**Touchpoints:** `backend/sim/types.py` (schedule + fallback fields on
`Threat`), `backend/sim/entities.py` (schedule consumer, flyover
detection, fallback), `backend/sim/red_ai.py` (spawn sets
`target_site_id` and optionally `maneuver_schedule`).

**Not doing now:** Boyu's policy layer that decides what schedule or
real-time override to emit. Chen produces the runtime hook + contract
doc; Boyu consumes it.

## Issue 12 — Cruise + future stealth cruise: double-op structure

- **State:** Cruise has a hard-coded S-pattern waypoint; stealth cruise
  does not exist as a kind
- **Category:** Rule refinement + new threat kind
- **Owner:** Chen (runtime) + Boyu (scheduler + terminal override) +
  Sebastijan (stealth cruise mesh, `models/`)
- **Merges with:** Issues 10, 11
- **Tier:** 2 (cruise schedule consumer) / 3 (contract publication) / 4
  (stealth cruise kind + model)

**What:**
- **Cruise (existing):** default target at spawn + optional pre-scripted
  maneuver schedule. No real-time override.
- **Stealth cruise (future kind):** same contract as cruise, plus the
  ability for Red AI to use `override_maneuver` during the terminal
  phase (near target), simulating HGV-lite late-phase evasion. Lower
  performance envelope than HGV, cheaper cost.

**Design target:**
- Cruise gains the `maneuver_schedule` field (same unified contract as
  Issue 10).
- The current hard-coded cruise S-pattern is retired in favour of a
  default `maneuver_schedule` populated by Red AI or a default generator.
- New threat kind `stealth_cruise`: same contract as cruise plus an
  "allow terminal override" flag.
- Stealth cruise mesh: Sebastijan reuses the current cruise mesh but
  swaps the round fuselage to a squared fuselage. Minor asset change.

**Touchpoints:** `backend/sim/types.py` (new `ThreatKind` +
allow-override flag), `backend/sim/config.py` (spec entry),
`backend/sim/entities.py`, `backend/sim/red_ai.py`,
`frontend/js/entities.js` (new mesh variant, coordinated with
Sebastijan).
